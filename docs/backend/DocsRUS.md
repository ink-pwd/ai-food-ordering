# Backend Service Overview

## Русский

### Что это за сервис

Backend — центральная часть системы AI Food Ordering.

Его задача — изолировать клиентов от прямой работы с Dots API и хранить всю основную бизнес-логику заказа еды в одном месте.

В дальнейшем к этому API могут обращаться разные клиенты, например:

* MCP-сервис для ChatGPT;
* Telegram-бот;
* другие внутренние сервисы.

Клиенту не нужно знать особенности Dots API, самостоятельно рассчитывать стоимость заказа или хранить состояние корзины. Он работает только с внутренним REST API backend-сервиса.

---

### Основной поток работы

Типичный пользовательский сценарий выглядит так:

```text
Client
  ↓
Session
  ↓
Catalog / Search
  ↓
Cart
  ↓
Contact information
  ↓
Price validation
  ↓
Order
  ↓
Dots API
```

#### 1. Session

Перед началом работы создаётся внутренняя сессия.

Она связывает конкретного пользователя или диалог с выбранным рестораном и используется для хранения контекста между запросами.

После создания backend возвращает `X-Session-Token`, который используется в следующих запросах.

---

#### 2. Catalog

Backend получает каталог ресторана из Dots API и сохраняет его локально в PostgreSQL.

В локальной базе хранятся:

* рестораны;
* категории;
* продукты;
* цены;
* доступность продуктов;
* связи между категориями и продуктами.

Синхронизация каталога выполняется асинхронно через RabbitMQ.

Redis используется для кеширования данных внешнего API и уменьшения количества одинаковых запросов в Dots.

Клиенты читают каталог уже через наш REST API и напрямую с Dots не взаимодействуют.

---

#### 3. Search

Поиск продуктов выполняется по локальной PostgreSQL базе.

Это позволяет не обращаться к Dots API при каждом поисковом запросе и предоставляет клиентам единый и быстрый интерфейс поиска.

---

#### 4. Cart

Корзина полностью управляется backend-сервисом.

Клиент передаёт только необходимые пользовательские действия, например:

* добавить продукт;
* изменить количество;
* удалить продукт.

Стоимость позиции и итоговая стоимость корзины рассчитываются backend-сервисом на основании сохранённых данных.

Клиент не может самостоятельно передать внутреннюю цену, итоговую сумму, restaurant ID или изменить состояние корзины.

---

#### 5. Contact information

Имя и телефон пользователя сохраняются внутри текущей сессии.

Перед созданием заказа backend проверяет наличие необходимых контактных данных и нормализует их перед отправкой во внешний API.

---

#### 6. Price validation

Локальная цена продукта не считается окончательной ценой заказа.

Перед созданием заказа backend отправляет корзину в Dots Price Validation API.

Это необходимо потому, что на стороне Dots могут действовать:

* акции;
* скидки;
* специальные правила расчёта;
* другие изменения стоимости.

Поэтому именно результат Dots является источником истины для финальной суммы заказа.

---

#### 7. Order

После успешной проверки корзины backend создаёт локальную запись заказа и отправляет заказ в Dots API.

Заказ содержит snapshot товаров на момент оформления, поэтому дальнейшее изменение каталога не меняет уже созданный заказ.

Создание заказа защищено через `Idempotency-Key`.

Повторный запрос с тем же ключом не создаёт второй заказ в Dots, а возвращает уже существующий локальный заказ.

---

### Статус заказа

После отправки заказа backend хранит его состояние локально.

Упрощённый lifecycle:

```text
creating
   ↓
created
```

Также поддерживаются состояния ошибок и другие внутренние статусы.

Если результат внешнего запроса неоднозначен, backend не пытается слепо повторять создание заказа, так как это могло бы привести к дубликату.

Статус такого заказа может быть уточнён отдельным запросом к Dots.

---

### Хранение данных

#### PostgreSQL

Используется как основное постоянное хранилище:

* restaurants;
* categories;
* products;
* carts;
* cart items;
* orders;
* order items;
* catalog synchronization logs.

#### Redis

Используется для быстрого временного хранения и кеширования данных.

В частности, Redis применяется для кеширования запросов к внешнему Dots API и runtime-данных приложения.

#### RabbitMQ

Используется для асинхронных операций.

На данный момент через очередь выполняется синхронизация каталога ресторана.

---

### Безопасность внутреннего API

API предназначен не для прямого публичного доступа пользователя, а для доверенных внутренних клиентов.

Все внутренние запросы защищены заголовком:

```text
X-Internal-Api-Token
```

Запросы, которым требуется пользовательский контекст, дополнительно используют:

```text
X-Session-Token
```

Для создания заказа также требуется:

```text
Idempotency-Key
```

Таким образом клиент не получает прямого контроля над внутренними идентификаторами, ценами и состояниями заказа.

---

### Роль Dots API

Dots остаётся внешней системой, через которую происходит фактическое создание заказа.

Backend выступает между клиентом и Dots:

```text
ChatGPT / MCP / Telegram
          ↓
     Laravel Backend
          ↓
       Dots API
```

Это позволяет не дублировать бизнес-логику в каждом клиенте.

MCP или Telegram должны только преобразовать действия пользователя в вызовы внутреннего API.

Расчёт корзины, проверка цен, состояние сессии, idempotency и работа с заказами остаются ответственностью backend-сервиса.

---

### Тестирование

Основные бизнес-сценарии покрыты автоматическими тестами.

Тесты работают с отдельной PostgreSQL базой.

Автоматический E2E-тест проходит полный внутренний сценарий:

```text
Session
  ↓
Contact
  ↓
Cart
  ↓
Product
  ↓
Price validation
  ↓
Order creation
  ↓
Idempotency check
  ↓
Order status update
```

При этом внешний Dots API мокается.

Таким образом тестируется реальное взаимодействие между слоями Laravel-приложения без создания настоящих заказов во внешней системе.
