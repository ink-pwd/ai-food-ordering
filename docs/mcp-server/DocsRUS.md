# MCP Server Overview

## Русский

### Что это за сервис

MCP-сервер — адаптер системы AI Food Ordering для взаимодействия с ChatGPT через протокол MCP.

Его задача — представить сценарий заказа еды в виде MCP tools, не перенося бизнес-логику из основного Laravel backend-сервиса.

MCP-сервис не взаимодействует с Dots Platform напрямую и не хранит собственную бизнес-базу каталога, корзин или заказов.

Архитектура выглядит так:

```text
ChatGPT / MCP Client
        ↓
     MCP Server
        ↓
  Laravel Backend
        ↓
    Dots API
```

MCP преобразует действия модели в доверенные REST-запросы к backend и возвращает безопасные структурированные результаты.

---

### Основной поток работы

Типичный сценарий заказа через ChatGPT выглядит так:

```text
get_restaurant_context
        ↓
set_customer
        ↓
Catalog / Search
        ↓
get_or_create_cart
        ↓
Cart operations
        ↓
get_cart
        ↓
Явное подтверждение пользователя
        ↓
create_order
        ↓
get_order_status
```

На всех этапах модель должна считать данные backend единственным источником фактической информации.

---

#### 1. Контекст заказа

Каждый новый сценарий заказа начинается с:

```text
get_restaurant_context
```

Инструмент создаёт новую backend-сессию с каналом `chatgpt` и автоматически сгенерированным внешним идентификатором сессии.

Ресторан выбирает backend. MCP не позволяет модели передавать или подменять restaurant ID, account ID или backend session token.

В ответ MCP возвращает безопасные данные ресторана и непрозрачный:

```text
session_handle
```

Клиент должен сохранить его и передавать без изменений во все инструменты, которым требуется сессия.

---

#### 2. Session handle

`session_handle` — представление доверенного backend-контекста заказа на стороне MCP.

Внутри него находятся:

* backend session ID;
* backend session token;
* доверенный slug ресторана;
* время истечения сессии;
* версия payload.

Payload защищён аутентифицированным шифрованием Laravel с использованием `APP_KEY` MCP-приложения.

Упрощённо:

```text
Backend session
      ↓
session ID + secret token + restaurant + expiration
      ↓
Laravel authenticated encryption
      ↓
opaque session_handle
      ↓
MCP Client
```

Модель не должна интерпретировать, изменять или самостоятельно формировать это значение.

Повреждённый, подменённый или истёкший handle отклоняется до выполнения требуемой backend-операции.

Так как handle шифруется через `APP_KEY`, изменение ключа приложения делает ранее выданные handles недействительными.

---

#### 3. Контактные данные

Контактные данные сохраняются через:

```text
set_customer
```

Инструмент принимает только:

* `session_handle`;
* `name` пользователя;
* `phone` пользователя.

Проверка и нормализация номера телефона остаются ответственностью backend.

MCP сам не помечает телефон подтверждённым и не возвращает модели нормализованный номер телефона. В безопасном ответе остаются имя пользователя и предоставленный backend флаг `phone_verified`.

---

#### 4. Каталог и поиск

Для работы с каталогом MCP предоставляет:

```text
get_categories
get_category_products
search_products
get_product
```

Ресторан всегда определяется из доверенного session context. Модель не может передать этим инструментам идентификатор другого ресторана.

Данные каталога возвращаются из backend без пересчёта или выдумывания.

К ним относятся:

* названия категорий;
* названия продуктов;
* описания;
* цены;
* акционные цены;
* валюта;
* ссылки на изображения;
* доступность товара.

Идентификаторы продуктов и категорий, которые видит MCP, являются локальными backend ID, а не идентификаторами Dots.

MCP не придумывает отсутствующие ингредиенты, модификаторы, диетические свойства, цены или доступность.

---

#### 5. Корзина

Для работы с корзиной используются:

```text
get_or_create_cart
get_cart
add_cart_item
update_cart_item
remove_cart_item
clear_cart
```

Жизненный цикл корзины, проверка продуктов, цены и итоговые суммы полностью контролируются backend-сервисом.

MCP-клиент может передавать только пользовательские действия:

* получить или создать текущую корзину;
* добавить товар;
* изменить количество строки корзины;
* удалить строку;
* очистить корзину.

MCP никогда самостоятельно не рассчитывает `unit_price`, `subtotal` или `total`.

`add_cart_item` принимает локальный backend `product_id`.

`update_cart_item` и `remove_cart_item` принимают `item_id` — это backend `CartItem.id`, полученный из массива `items` текущей корзины.

Эти идентификаторы различаются:

```text
product_id → Product.id
item_id    → CartItem.id
```

Их нельзя использовать взаимозаменяемо.

`add_cart_item` не создаёт корзину неявно. Для нового контекста заказа при отсутствии активной корзины сначала необходимо вызвать `get_or_create_cart`.

---

#### 6. Подтверждение оформления

Создание заказа дополнительно защищено правилом явного подтверждения на уровне MCP.

Перед `create_order` клиент должен получить актуальную корзину через:

```text
get_cart
```

Пользователю необходимо показать текущие товары, количества и итоговую сумму, возвращённую backend.

После этого пользователь должен явно подтвердить создание заказа.

Только после явного подтверждения разрешён вызов:

```json
{
  "session_handle": "...",
  "confirmation": true,
  "delivery_time": 0
}
```

Сам просмотр корзины, вопрос о цене или обсуждение оформления не считаются подтверждением.

Если `confirmation` отсутствует, равно `false` или не является literal boolean `true`, операция отклоняется ещё до восстановления сессии и выполнения HTTP-запросов.

---

#### 7. Создание заказа

`create_order` не позволяет модели передавать цены, итоговые суммы, cart ID, restaurant ID, Dots ID или `Idempotency-Key`.

Flow выглядит так:

```text
MCP confirmation
      ↓
Восстановление доверенного session_handle
      ↓
GET текущей корзины из backend
      ↓
Генерация внутреннего Idempotency-Key
      ↓
POST delivery_time в backend
      ↓
Backend price validation / order flow
      ↓
Безопасный MCP-ответ заказа
```

Внутренний ключ идемпотентности формируется только из доверенных backend-данных:

```text
SHA-256("mcp-order:{backend-session-id}:{cart-id}")
```

Модель не может передать этот ключ, и MCP не возвращает его наружу.

В теле запроса создания заказа MCP отправляет только `delivery_time`. Контактные данные, идентификаторы ресторана и Dots, настройки получения и оплаты, товары корзины, проверка цен, итоговая стоимость и фактическое создание заказа в Dots остаются ответственностью backend.

`delivery_time = 0` означает «как можно скорее». Положительное значение — будущая Unix timestamp для запланированного самовывоза.

POST создания заказа выполняется только один раз за вызов tool. MCP не повторяет создание заказа автоматически после timeout, ошибки соединения или неоднозначного checkout-результата, поскольку слепой retry может привести к дублированию заказа во внешней системе.

---

#### 8. Статус заказа

Текущее авторитетное состояние заказа получается через:

```text
get_order_status
```

MCP запрашивает текущий заказ у backend и возвращает только безопасное whitelisted-представление.

При этом backend может обратиться к Dots и сохранить обновлённый статус. Поэтому tool не считается полностью read-only, хотя сам не выполняет деструктивного пользовательского действия.

Модель не должна самостоятельно придумывать статус заказа или обращаться к Dots напрямую.

### MCP tools

Сейчас сервер предоставляет 14 tools:

| Tool | Ответственность |
| --- | --- |
| `get_restaurant_context` | Создать доверенный контекст заказа |
| `set_customer` | Сохранить имя и телефон пользователя |
| `get_categories` | Получить актуальные категории ресторана |
| `get_category_products` | Получить товары выбранной категории |
| `search_products` | Выполнить поиск по backend-каталогу |
| `get_product` | Получить актуальные данные одного товара |
| `get_or_create_cart` | Получить активную корзину или создать новую |
| `get_cart` | Получить текущую активную корзину |
| `add_cart_item` | Добавить продукт в корзину |
| `update_cart_item` | Изменить количество строки корзины |
| `remove_cart_item` | Удалить одну строку корзины |
| `clear_cart` | Очистить текущую корзину |
| `create_order` | Создать заказ после явного подтверждения |
| `get_order_status` | Получить текущее авторитетное состояние заказа |

MCP resources и prompts сервер сейчас не предоставляет — интерфейс заказа реализован полностью через tools.

### Взаимодействие с backend

Все HTTP-запросы к ordering backend изолированы в:

```text
App\Integrations\OrderingBackend\OrderingBackendClient
```

Отдельные MCP tools не используют Laravel HTTP client напрямую.

Каждый запрос в backend содержит:

```text
X-Internal-Api-Token
```

Запросы, которым требуется пользовательская сессия, дополнительно содержат доверенный:

```text
X-Session-Token
```

При создании заказа также передаётся внутренне сгенерированный:

```text
Idempotency-Key
```

Эти значения являются инфраструктурными секретами и никогда не передаются как управляемые моделью MCP-аргументы.

URL backend, internal API token и timeout настраиваются через environment MCP-сервиса.

---

### Source of truth и безопасность ответов

MCP считает backend источником истины для:

* выбора ресторана;
* каталога;
* доступности продуктов;
* обычных и акционных цен;
* состояния корзины;
* итогов корзины;
* состояния подтверждения контакта;
* итоговой суммы заказа;
* статуса заказа.

Перед передачей данных модели MCP проверяет структуру backend-ответа.

Выходные данные формируются через явный whitelist. Внутренние и внешние поля, которые модели не требуются, удаляются.

Например:

* backend session token никогда не возвращается отдельным полем;
* Dots product IDs удаляются из результатов корзины и заказа;
* сырой `failure_message` заказа от backend/Dots не передаётся модели;
* внутренний `Idempotency-Key` не возвращается наружу;
* неожиданный формат backend-ответа считается некорректным и отклоняется.

Так внутренние детали реализации и секреты не попадают в model context.

---

### Обработка ошибок

Ошибки backend и транспорта преобразуются в безопасные MCP-ошибки.

MCP различает, например:

* ошибку авторизации;
* отсутствие ресурса;
* конфликт текущего состояния;
* validation/checkout rejection;
* некорректный backend-ответ;
* ошибку соединения;
* недоступность backend-сервиса.

Сырые тела backend-ответов, токены и технические transport details модели не передаются.

При checkout backend `422` преобразуется в пользовательское сообщение о том, что ресторан, возможно, сейчас не принимает заказы или выбранное время получения недоступно, без раскрытия сырой ошибки Dots.

После ошибки создания заказа MCP не выполняет автоматический retry.

---

### Языковая политика

Вся human-facing и model-facing коммуникация MCP написана на русском языке.

Это касается:

* server instructions;
* названий tools;
* описаний tools;
* описаний input schema;
* validation messages;
* безопасных сообщений ошибок;
* инструкций по подтверждению заказа.

Технические идентификаторы остаются без изменений:

* имена MCP tools;
* ключи structured output;
* HTTP headers;
* REST paths;
* status values.

Названия и описания ресторанов, категорий и продуктов, полученные от backend, сохраняются без перевода и изменения. MCP не переписывает и не придумывает эти фактические данные.

---

### Хранение состояния

MCP-сервис не хранит собственное бизнес-состояние ресторанов, продуктов, корзин или заказов.

Доверенное состояние заказа остаётся в backend.

На стороне MCP контекст между вызовами переносится внутри зашифрованного `session_handle`. Поэтому сам adapter фактически остаётся stateless между tool calls при условии, что клиент сохраняет handle, а `APP_KEY` приложения остаётся неизменным.

---

### Тестирование

MCP-сервис покрыт автоматическими тестами на уровне HTTP-интеграции с backend и MCP tools.

Текущий набор тестов:

```text
163 tests
911 assertions
```

Тесты покрывают:

* MCP discovery и регистрацию tools;
* backend HTTP headers и timeout;
* безопасный mapping backend-ошибок;
* некорректные backend-ответы;
* connection и timeout failures;
* создание и восстановление зашифрованного `session_handle`;
* подмену и истечение handle;
* инициализацию restaurant context;
* работу с контактными данными;
* категории и продукты каталога;
* поиск продуктов;
* создание и чтение корзины;
* add/update/remove/clear операции корзины;
* корректное использование `product_id` и `item_id`;
* обязательное явное подтверждение заказа;
* внутренние idempotency keys;
* защиту от небезопасного повторного создания заказа;
* создание заказа;
* получение статуса заказа;
* output whitelisting;
* скрытие backend tokens, Dots identifiers и сырых failure details.

В автоматических MCP-тестах внешний backend HTTP boundary мокается, поэтому реальные заказы в Dots не создаются.

Реальный интеграционный сценарий проверяется отдельно через MCP Inspector или другой MCP-клиент с запущенным backend-сервисом.
